# 户型到灰模：三维结构层实施方案

版本：v2（2026-10-27）。v1 以 Blender 为主引擎、校核用视觉模型判断、灰模不含家具，三处均已推翻，本文为准。

面向 0.5.x。目标不是复刻视频里的 Agent 演示，而是在现有画布下面补一层**可计算的三维结构**，让多机位出图不再依赖图像模型"猜空间"。

## 1. 精度定位

先把话说死：交付物是 AI 生成图，它的精度上限由图像模型决定，不由几何决定。所以本方案承诺的是——

> **结构可测量地准确，材质光影归 AI。**

可测量，指的是能给出数字、能回归测试、达不到就标红交人工。不承诺"一张模糊平面图一键出 95% 准确成品"，那是数据不足，不是技术问题。

第一版限制：住宅、正交墙体、用户提供主要尺寸（开间、进深、层高）。斜墙、弧形墙、复式挑空不进第一版，明确拒绝并说明原因，不做半吊子支持。

## 2. 误差链

从用户尺寸到交付图共五段，只有第四段无法归零：

| 段 | 性质 | 说明 |
|---|---|---|
| 尺寸 → 户型数据 | 可校核 | 人工确认后不再丢精度 |
| 户型数据 → 灰模几何 | 无损 | 脚本解析构建，坐标即结果 |
| 灰模 → 相机投影 | 无损 | 渲染与校验共用同一套矩阵 |
| 投影 → 图像模型 | **有损，主误差源** | 只能压，不能消 |
| 生成图 → 结构校核 | 可量化 | 有真值可比，不许靠猜 |

方案的所有设计都服务于两件事：**把第四段的漂移压到最小**，**把第五段从"猜"改成"算"**。

## 3. 分层与引擎选型

```text
户型数据层     plans[]  项目级结构化户型，不挂在图片节点上
    ↓
识别层        视觉模型读平面图 → 户型 JSON 初稿（允许不准，必须人工校核）
    ↓
几何层        massing-backend 接口
              ├─ three：渲染进程内，主力
              └─ blender：子进程，异形/复杂布尔/终稿时才用
    ↓
出图层        灰模 + 深度 + 边线，进 generator 独立端口
    ↓
校核层        几何投影对齐打分 + 有限次自动重跑 + 人工确认
    ↓
交付层        layout / quote / delivery（已有，不改）
```

**主力是 three，不是 Blender。** 理由是投影矩阵同源：渲染用的相机和校验用的投影是同一个 `Matrix4`，一个误差点都不多。Blender 要导出相机参数再在 JS 里重建，多一次转换就多一个可能出错的面。

分发上也更干净：three 在渲染进程里跑，零安装、毫秒级、机位拖动可实时预览。Blender 要用户装 1GB 多，还锁版本。

Blender 降级成可选后端，只在三种情况启用：异形或曲面墙、需要真布尔的复杂开洞、终稿要 Cycles 级物理准确阴影。

## 4. 户型数据契约

存项目级 `plans`，与 `rooms`、`materials` 同级，不进图片节点。单位统一毫米，Z 向上，原点取户型外包框左下角。

```json
{
  "schemaVersion": 1,
  "units": "mm",
  "floorHeight": 2800,
  "ceiling": { "height": 2600, "beams": [{ "a": [0,0], "b": [4150,0], "width": 200, "drop": 400 }] },
  "wallThickness": { "exterior": 240, "interior": 120 },
  "walls": [
    { "id": "w1", "a": [0, 0], "b": [4150, 0], "thickness": 240, "type": "exterior" }
  ],
  "openings": [
    { "id": "win1", "wallId": "w1", "kind": "window", "offset": 1200,
      "width": 1800, "height": 1500, "sill": 900 },
    { "id": "d1", "wallId": "w1", "kind": "door", "offset": 3200,
      "width": 900, "height": 2100, "sill": 0 }
  ],
  "rooms": [
    { "id": "r1", "name": "客厅", "polygon": [[0,0],[4150,0],[4150,3300],[0,3300]] }
  ],
  "furniture": [
    { "id": "f1", "blockId": "sofa-3", "roomId": "r1", "pos": [900, 2600],
      "yaw": 0, "scale": 1 }
  ],
  "cameras": [
    { "id": "c1", "roomId": "r1", "pos": [1200, 900],
      "yaw": 45, "height": 1500, "focal": 24 }
  ]
}
```

必须固定的设计：

- **门窗用 `offset` 而不是绝对坐标**。`offset` 是沿墙 `a → b` 方向的起点距离。墙体移动或拉长时门窗自动跟随，不会脱开。这是户型能被反复编辑的前提。
- **墙体是线段 + 厚度**，不是闭合多边形。开洞不用通用布尔：一段墙带一个洞，解析成"左垛 + 右垛 + 过梁 + 窗台"四个体块拼起来，精确且零成本。three 和 Blender 都能这么建。
- **必须有 `ceiling`**。没有吊顶标高和梁位，模型自己编，净高就飘，家具比例跟着失真。
- **必须有 `furniture`**。灰模不含家具，图像模型照样随便摆，"家具位置"的问题一点没解决。用体块库：沙发 1800×900×750、双人床 1500×2000、餐桌 1400×800×750、衣柜深 600、马桶 700×400、台面高 850……十几个基础体块覆盖八成住宅。**位置由数据定，长相由模型定。**
- **机位是二维位置 + 朝向 + 视高 + 焦距**，不是相机矩阵。设计师在平面图上放点，脚本换算。室内默认 24mm、视高 1500mm、相机水平（两点透视）。
- **画幅必须锁定**。灰模与出图同 aspect，留裁切安全区，定稿后禁止裁切，否则构图会重排。

校验规则（写入时拦截，不等到建模才报错）：

1. 每段墙长度 > 0，且必须正交（`ax===bx` 或 `ay===by`）。
2. 每个 `opening.wallId` 必须存在；`offset + width ≤ 墙长`。
3. 门窗 `sill + height ≤ 净高`。
4. 房间多边形必须闭合且不自交。
5. 机位必须落在某个房间多边形内部。
6. 相邻平行墙间距不得小于两者厚度之和（防穿墙）。
7. 家具体块不得与墙体相交，且必须整体落在房间内。
8. 同一墙段上门窗不得重叠。

## 5. 后端接口与命令白名单

`massing-backend` 是一层薄接口，两个实现共用同一组命令语义：

| 命令 | 输入 | 说明 |
|---|---|---|
| `build` | 整份户型 JSON | 清空场景、建墙、开洞、吊顶梁、体块家具 |
| `setCamera` | 机位数组 | 按二维机位换算相机，覆盖已有 |
| `render` | `{kinds:[], size}` | 出灰模 / 深度 / 边线，返回文件 |
| `preview` | 户型 JSON | 低模快速预览，户型编辑时实时看三维 |

没有 `exec`、没有 `eval`、没有任意 `--python-expr`。MCP 只作为 Agent 接入的**接口形态**保留，正式产品执行的是固定命令。

**blender 后端**：主进程把命令组装成 `job.json` 写进临时目录，交给固定入口脚本。

```text
blender.exe -b --factory-startup -noaudio --python runner.py -- --job job.json
```

- 锁 **Blender 4.5 LTS**。4.2 已于 2026 年 7 月 EOL，不得再用。
- `--factory-startup`：不读用户配置，避免插件和启动项污染结果。
- 渲染用 `BLENDER_WORKBENCH`，CPU 渲染，不用 Cycles。灰模不需要材质精度。
- 硬超时 120 秒，取消时 kill 子进程并清临时目录。
- 对象统一前缀（`GW_WALL_*`、`GW_OPEN_*`），便于清理排错。

**three 后端**：渲染进程内构建 `BufferGeometry`，输出走离屏 WebGL。弱显卡黑图时降级 SwiftShader 软件光栅，并在状态栏明示"当前为软件渲染"。绝不静默降级到另一个后端——几何结果可能不同，用户会以为是软件不稳定。

## 6. 部署形态

Blender 便携包 `blender-4.x-windows-x64.zip` 约 **365～383 MB**，装完约 **1.1 GB**。这不是加一个依赖，是让设计师多装一个三维软件。

| | 用户要动手 | 体积 | 版本一致性 | 断网可用 |
|---|---|---|---|---|
| A 用户自装 + 探测 | 下载、安装、最好装默认路径 | 0 | 差 | 是 |
| B 按需下载便携版到本地 | 不用安装，首次等 370MB | 本地 ~1.1 GB | 好 | 下载后可 |
| C 云端渲染 | 完全不用管 | 0 | 最好，服务端锁死 | 否 |

**推荐顺序：three 打穿全链路 → 云端 Blender（C）兜异形户型 → 本地装 Blender（A）作为高级用户加速项。B 不做。**

B 是最尴尬的中间态：用户没省掉等待，我们还得管下载源、校验、解压、杀软误报，最后一样占 1GB 硬盘。

C 更划算也更准：Workbench 是 CPU 渲染，不需要 GPU 机器；上传的是几 KB 的户型 JSON，不是图片；回传 4 张灰模 PNG 不到 1MB。一台普通云主机一天能跑几千套。更关键的是**版本锁死，"同一户型重跑像素级一致"这个验收指标才成立**。

核心链路任何环节都不依赖用户环境——这是选型的硬约束。

GPL 边界：只做子进程调用、不链接、不修改，不构成衍生作品。若要随包分发 Blender 二进制，需随包提供对应源码获取方式（指向 blender.org 对应版本）。不分发则完全绕开。

## 7. 节点接入

新增两个节点类型，走现有注册表，不改画布主流程。

`graph-core.js` 的 `NODE_DEFS` 加：

```js
floorplan: {
  title: '户型',
  inputs: [{ id: 'reference', type: PORT.MEDIA, max: 1 }],
  outputs: [
    { id: 'geometry', type: PORT.GEOMETRY },
    { id: 'out', type: PORT.MEDIA }
  ]
},
massing: {
  title: '灰模',
  inputs: [{ id: 'geometry', type: PORT.GEOMETRY, required: true, max: 1 }],
  outputs: [{ id: 'out', type: PORT.MEDIA }]
}
```

`PORT` 加 `GEOMETRY: 'geometry'`。端口类型独立的好处是：户型节点只能连灰模节点，物理上进不了生成节点的图片槽位。

两个节点都遵守既定外壳规范（408px 高、顶部框架 / 中部内容 / 22px 底栏、疏密变量档位），不新增一套尺寸。

- **户型节点**：中部是 Konva 二维编辑器（复用画布已有能力，不引入 3D 依赖）。左侧输入口接平面图作底图描图，右侧出结构化户型。双击进放大编辑器：画墙、开门窗、放家具、放机位。
- **灰模节点**：中部是机位缩略图网格 + 一次渲染按钮。按机位自动在右侧创建图片节点，与现有"生成结果作为结果节点出现"的行为一致。

## 8. 出图输入：三件套

灰模**不够**。深度图和边线是唯一能让图像模型锁死结构的手段，必须一起喂——我们的模型（NanoBanana Pro / Gemini 3 Pro Image / Seedream 5.0 Pro）都支持多图参考，三件套的结构贴合度明显高于单张灰模。

这意味着**要给 `generator` 加独立端口**，不能塞进 `structure` 槽位：`canvas.js` 的 `cameraInputs` 会把多个 `structure` 输入理解为"多楼层"或"多机位"（`planMode` 分支），第 5 个输入会被当成第二个机位，提示词会串。

```js
// graph-core.js generator 增加
{ id: 'depth', type: PORT.MEDIA, required: false, max: 1 },
{ id: 'edge',  type: PORT.MEDIA, required: false, max: 1 }
```

prompt 侧只在 `depth` / `edge` 存在时追加一段几何约束说明，明确它们是"几何硬约束"，与 `style` 的"外观参考"语义区分。这个改动属于 P0/P1，不推后——为工程省事而放弃精度是本末倒置。

`rerollConsistencyPrompt` 的优先级链（结构 > 局部修改 > 明确材质 > 灯光 > 同组一致性）和 `rerollSiblingNodes` 的兄弟机位参考**完全不用改**，直接生效。结构变成真的以后，这两套机制的效果会高一个量级。

## 9. 校核

三层，从便宜到贵。

**1. 几何自检**（本地，零成本）：第 4 节的八条校验规则，建模前跑一遍。

**2. 几何投影对齐**（本地，零 API 成本）：把 3D 几何按同一套相机矩阵投影到图像平面，得到墙体、洞口、家具轮廓的精确像素位置；对生成图做边缘检测，比较重合度。输出两个数字：

- **墙体投影 IoU**，容差 ±2px 膨胀，合格线 **≥ 0.90**
- **门窗洞口中心像素偏差**，合格线 **≤ 画幅宽度 1.5%**

不合格走有限次自动重跑（默认 2 次），超过标红交人。有真值在手，不该让视觉模型去猜结构——它不如一行投影代码。

**3. 语义校核**（视觉模型，一次调用）：只判它擅长的事——材质是否延续、软装气质是否一致、画面是否合理、有没有明显穿模或悬浮。不判结构。

**4. 人工确认**（必须存在）：校核通过后仍停在人工关卡，由设计师点"定稿"。

人工关卡不用造新机制。`workflow-runtime.js` 的 `runDag` 已经支持：

```js
if (node.executionMode === 'manual') {
  result = { status: 'waiting', message: node.manualReason || '等待人工操作' };
}
```

灰模节点给 `executionMode: 'manual'`、`manualReason: '请核对墙体、门窗与家具后确认'`，群组运行会自然停在这里，下游分支标 `skipped`，不会继续烧钱。

## 10. 交付衔接

后半段全部现成，不新增：效果图 → `tool` 局部重绘 → `material` 空间材质 → `layout` 版式 / `quote` 报价 / `delivery` 交付。

与视频最大的形态差别：视频把所有产物塞在一个聊天框里，靠文件夹管理；我们每一步都是节点，整套"户型 → 灰模 → 四机位 → 材质 → 局部改 → 排版"可以存成工作流模板一键重放（`studio-tools.js` 的资产库已支持节点模板导入导出）。

## 11. 分期

### P0 打通几何全链路

- 户型数据契约 + 八条校验 + 单元测试。
- 户型节点二维编辑器：画正交墙、开门窗、放家具体块、放机位、手输尺寸。
- `massing-backend` 接口 + three 实现：`build` / `setCamera` / `render` / `preview`。
- 灰模、深度、边线三件套回写画布；`generator` 加 `depth` / `edge` 端口。
- 几何投影对齐算法 + 打分，纯 Node 可测。

验收：手输一套三室两厅（约 40 段墙、12 个洞口、20 件家具），4 机位三件套全链路 < 6 秒；户型 JSON 与渲染结果坐标逐段核对为 0 偏差；重跑像素级一致。

### P1 接识别与人工校核

- 视觉模型读平面图出户型初稿（复用 `providers.js` 视觉配置），允许大面积不准。
- 户型编辑器校核态：低置信墙段标黄、尺寸缺失标红、房间面积与图上标注对不上时提示。
- 尺寸标注（4150 / 2960 这类）单独做一轮 OCR 对齐，尺寸才是一切精度的根。

验收：从上传平面图到 4 机位效果图，点按次数 ≤ 8；不改墙线的情况下，生成图墙体 IoU 中位数 ≥ 0.90，不合格标红率 < 15%。

### P2 闭环与增强

- 语义校核接入 + 失败原因归类 + 自动重跑策略调优。
- 云端 Blender（C）：异形户型、复杂布尔、终稿阴影。
- 灰模进全景节点，出 360° 漫游。

## 12. 风险

| 风险 | 应对 |
|---|---|
| 弱显卡 WebGL 黑图 | SwiftShader 软渲染兜底，状态栏明示；Blender 是 CPU 渲染，天然无此问题 |
| 平面图识别不准，用户不敢信 | 第一版不做"一键"，识别只填空，必须过人工校核；低置信度可视化 |
| 异形户型 | 第一版明确拒绝并说明；P2 交给云端 Blender |
| 体块家具不够用 | 先上 12～20 个基础体块覆盖八成，缺的让用户用矩形体块自定义尺寸，不追求型号级还原 |
| 用户环境差异导致不可复现 | 核心链路放服务端锁版本；本地渲染只作加速项，结果需过同一套投影对齐校验 |
| GPL 边界 | 只子进程调用，不分发修改版；若分发二进制需附源码获取方式 |
| 数据契约反复 | 契约一旦进项目文件就要带 `schemaVersion` 并写迁移，P0 前定死，之后只加不改 |

## 13. 回归

新增测试（`node --test`，全部纯 Node，不依赖浏览器和 Blender）：

- `tests/floorplan-contract.test.js`：八条校验的正反例，含 offset 越界、非正交墙、机位在房间外、家具穿墙、门窗重叠。
- `tests/geometry-projection.test.js`：给定户型与机位，断言投影出的墙线端点像素坐标；断言投影与光栅边缘的 IoU 计算正确。
- `tests/massing-backend.test.js`：命令白名单拒绝非法命令；超时与取消路径；后端切换不改变输出契约。
- `tests/furniture-blocks.test.js`：体块库尺寸表完整性，摆放后 AABB 不与墙体相交。

Blender 相关不进 CI（环境依赖太重），改为本地冒烟脚本 `tests/massing-smoke.mjs`，固定户型跑通 build → render → 校验输出尺寸与投影一致性。
