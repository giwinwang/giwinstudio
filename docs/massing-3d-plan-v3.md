# 户型三维管线 · v3 增补方案

版本：v3（2026-10-27）。**取代 `massing-3d-plan.md` v2 的第 3、7、8、9、11 节**，其余（第 1 精度定位、第 2 误差链、第 4 数据契约、第 10 交付衔接）继续有效，不改。

改这一版的唯一原因：v2 假设"视觉模型识别平面图"是唯一入口。实际主用户是设计师，主入口是 DXF 源文件。前提变了，P0 的范围、编辑器形态、验收指标必须跟着变。

---

## 1. 结论先写在这

1. **主路径 = DXF 解析 → 图层映射 → 户型 JSON；位图识别降为兜底。** 设计师手上有源文件，让他描图是倒退。
2. **编辑器的主形态是"校对"，不是"绘制"。** 从 40 段墙里从零画一遍，没人受得了；校对 8 处标黄的地方，人人接受。
3. **P0 不含云端、不含 Blender、不含视觉模型。** 一条本地纯 JS 链路走通，验收指标全部可测。

---

## 2. 输入层：三档，汇入同一份契约

```
DXF（主）   ── 解析 ──┐
矢量 PDF    ── OCR ──┼──→  floorplan.json  ──→ 几何层 ──→ 三通道出图
位图        ── 识别 ──┘        （唯一真源）
```

三档的差别只在"怎么得到这份 JSON"，下游一行不改。这是本方案最重要的一条结构性约束：**几何层只认契约，不认来源。**

| 档 | 拿到什么 | 需要用户做什么 | 位置误差 |
|---|---|---|---|
| DXF | 坐标即真值，图层即构件 | 确认图层映射（首次可存模板） | ~0 |
| 矢量 PDF | 标注是文本，可 OCR 读数值 | 拉一次标尺 | 30~60mm |
| 位图 | 只有像素 | 拉标尺 + 校对尺寸 | 50~100mm |

**DXF 档不调用视觉模型，零 API 成本。** 主路径免费，兜底路径才计费。

**DWG 不在支持范围**（二进制，纯 JS 解不了）。V1 提示"另存为 DXF"；P2 做云端转换（几 KB 上传、秒级返回、无 GPU），配显式同意 + 转完即删的声明。

## 3. DXF 导入：三个必须自己写的算法

这三个算法是 DXF 路径的全部难点，v2 里一条都没有。全部纯 JS，可 `node --test` 覆盖，不碰渲染。

### 3.1 解析器：自己写，不引包

DXF 是 ASCII 组码流（`0/SECTION`、`0/LINE`、`8/图层名`、`10/20/11/21`…）。第一版只需要 `LINE`、`LWPOLYLINE`、`ARC`、`CIRCLE`、`INSERT`、`TEXT`、`MTEXT`、`HATCH` 八种实体和 `$INSUNITS`、`$EXTMIN/$EXTMAX` 两个头变量，约 300 行。

不引 `dxf-parser` 的理由：它把 block 嵌套、代理对象、扩展数据全展开，我们用不到；自己写可以**在遇到 `ACAD_PROXY_ENTITY` 时直接给出可读报错**（"这张图是天正自定义对象，请图形导出为基本对象"），而不是解析出空结果让用户懵。供应链上也少一个依赖。

### 3.2 双线 → 墙中心线

CAD 里墙体通常是两条平行线（内外面），契约要的是"中心线 + 厚度"。算法：

1. 取映射为"墙"图层的所有线段，按方向分两族（水平 / 垂直）
2. 同族内两两配对：平行、投影重叠 > 60%、间距 ∈ [60, 400] mm
3. 配对成功 → 中心线 = 两线中点连线，厚度 = 间距
4. 未配对的墙层线段 = 单线墙 → **线即中线，两侧各扩半个墙厚**，墙厚由用户输入，不猜（见 3.4）
5. 中心线端点延长到相交（处理 L 角缺口），再按相交裁剪（处理 T 角多余段）

配对失败率是这个环节的健康指标。超过 20% 就该提示用户"这张图的墙线不规整，建议先检查图层"。

### 3.4 单线墙：问用户，不猜

单线只知道墙在哪，不知道多厚、也不知道线是墙的哪一面。唯一自洽的约定是"线即中线，两侧各扩一半"，
所以缺的那个量只能问：

- 不给厚度 → 不生成墙，返回 `NEED_SINGLE_LINE_THICKNESS`（`blocking:true`），带 `action` 供界面直接弹框
- 给了厚度 → 生成墙并标 `inferred:true`，附 `SINGLE_LINE_INFERRED` 提示哪几段是推断的
- **内外墙要分开给**：住宅外墙 240、内墙 120，只给一个值厚度配对掉到 53%。分类依据是"墙中线是否落在外包框边上"

有一个无法从几何上区分的情况：单线画法（线=中线）与双线丢了一半面线（线=面）在图上完全一样。
按中线处理时后者会整体偏半个墙厚——实测同一套参数下真单线 100%、丢半面线 18%。
所以提示文案必须明写这句话，交人工确认关卡兜底。

### 3.3 断口配对 → 门窗 offset

墙线在洞口处是**断开**的，门窗是**块**（`INSERT`）。契约里 `opening` 用 `offset`（沿墙 a→b 的起点距离），所以要做：

1. 沿每段墙的中心线找"断口"（线段之间的空隙）
2. 在断口附近搜门窗图层的 `INSERT`，取插入点投影到墙线上
3. `offset` = 投影点 − 断口起点；`width` = 断口长度（**以断口为准，不以块尺寸为准**——块常带门套放大）
4. 断口无对应块 → 标为"疑似洞口"待用户确认；有块无断口 → 忽略（多半是家具块误入）

第 3 步的取舍很关键：断口是几何事实，块是符号，冲突时信几何。这条写进代码注释，别让后人改回去。

### 3.4 归一化（工程坑，必做）

DXF 的原点常在几十万毫米外（图纸是局部截取），直接喂 three 会因 32 位浮点精度不足出现可见抖动。所以解析后必须：

- **平移到外包框左下角**，让所有坐标落在 [0, 20000] 内（契约第 4 节本来就要求原点在左下角，正好对上）
- **单位判定**：先读 `$INSUNITS`；为 0（未定义）时用对角线反查——住宅 8~15m，算出 8000 即毫米，算出 8 即米
- **旋转对齐**：若主墙方向不在 0°/90° 的 ±1° 内，按主轴角度反向旋转，让轴网回到正交

旋转对齐这一步容易被跳过，后果是白模整体斜着，机位朝向全歪。

## 4. 编辑器：校对，不是绘制

v2 P0 里最贵的一项是"画正交墙"。设计师 CAD 里已经画好了，让他再画一遍等于宣布这功能不可用。

**主形态**：DXF 导入后直接进校对面板，标黄的是待确认项。

| 区域 | 内容 |
|---|---|
| 左侧 | 平面图底图（或 DXF 线框重绘），叠加房间编号、墙线高亮、洞口标记 |
| 右侧 | 全局参数（层高 / 外墙厚 / 内墙厚）+ 房间表 + 门窗表 |
| 顶部 | 图层映射（仅 DXF 档出现，可存模板） |
| 底部 | 实时校验条 + 生成按钮 |

三条交互要求，都是"给设计师"而不是"给普通用户"的差别：

1. **表格直接编辑**，Tab 跳格、Enter 提交、数字直接输；不要向导式一页页问
2. **批量操作**：框选十段墙一次改厚度；同层所有门一次改类型
3. **允许专业参数裸露**：视高、焦距、机位数量不要藏成黑盒

**兜底保留**：画墙、拆墙、合并房间三个操作要有，但放在"编辑"态而不是主流程。不做自由绘制墙线（斜墙第一版明确拒绝）。

**拒绝要前置**：导入时就检测非正交墙段，列出来告诉用户"这 3 段斜墙第一版不支持"，别等校对到一半才报错。

## 5. 出图：三个通道，四个技术细节

v2 的三件套（灰模 / 深度 / 边线）方向对，但实施时有四个点没定，每个都会返工。

### 5.1 深度图必须固定 near/far

给图像模型用的深度图是**近白远黑**的归一化灰度。若每张图各自按场景自适应缩放，同一户型的四个机位深度尺度就不一致，模型会读错空间关系——比不用还糟。

- `near = 100mm`，`far = 户型外包框对角线 × 1.2`（同一份户型内所有机位共用同一组值）
- 输出 16bit PNG（下游控图用，动态范围够）
- 另存一张 8bit 灰度预览（给人眼看，判断干不干净）

### 5.2 边线图用几何算，不用图像后处理

不要对灰模跑 Sobel——噪声大、脏边多。用 `EdgesGeometry`（夹角阈值 30°）直接渲染线框，只保留垂直于视线的边。产物是干净的结构线稿，线宽可控，还能只画墙和洞口、不画家具。

### 5.3 编码用 toBlob 不用 toDataURL

四机位 × 三通道 = 12 张图。`toDataURL` 是同步 base64，12 次会把主线程卡死。用 `toBlob` + `createImageBitmap` 异步流水，配合 4 张一批的并发上限。

### 5.4 端口必须独立

v2 说的这条我同意，补一个实现依据：`canvas.js` 的 `cameraInputs` 把多个 `structure` 输入理解成"多机位/多楼层"（`planMode` 分支），三件套塞进 `structure` 会让第 2、3 张深度/边线被当成第二个机位，提示词直接串。所以 `depth` / `edge` 必须是新端口类型，物理上不可混。

命名分两层：端口叫 `depth` / `edge`（工程语义），界面显示**"白模 / 深度 / 线稿"**（设计师语言）。

## 6. 校核：把 IoU 换成 Chamfer

v2 用"墙体投影 IoU ≥ 0.90，容差 ±2px"。这条我建议改，理由很具体：**IoU 对平移极度敏感**。生成图相对灰模整体偏 3px，IoU 就会掉到 0.85 以下，触发自动重跑；而 3px 在 1024 画幅上只有 0.3%，肉眼完全看不出。结果是大量正确结果被判死，白烧调用。

改用**双向 Chamfer 距离**（对外轮廓线做距离变换，求双向平均最近距离），平移鲁棒，且能给出"偏了多少像素"这种可解释的数字：

| 指标 | 算法 | 合格线 |
|---|---|---|
| 结构贴合 | 双向 Chamfer，归一化到画幅宽 | 中位数 ≤ 1.2% 画幅宽 |
| 方向一致性 | 主导墙线角度直方图交叉相关 | ≥ 0.85 |
| 洞口位置 | 门窗中心点最近邻距离 | ≤ 1.5% 画幅宽 |

三层顺序不变：几何自检（零成本）→ 投影比对（零 API）→ 语义校核（一次调用，只判材质与合理性，不判结构）。人工定稿关卡照旧用 `workflow-runtime.js` 的 `executionMode: 'manual'`。

## 7. 模块落位

按仓库现有平铺习惯（`canvas.js` / `graph-core.js` / `workflow-runtime.js` 同级），不新建 `src/` 目录：

```text
floorplan-schema.js     契约定义 + 13 条校验 + schemaVersion 迁移   纯逻辑
dxf-parse.js            组码流 → 原始图元（8 种实体 + 头变量）       纯逻辑
dxf-topology.js         双线合并 / 断口配对 / 归一化                 纯逻辑
dxf-layers.js           图层统计 + 映射模板读写                     纯逻辑
massing-backend.js      命令白名单 build/setCamera/render/preview   接口层
massing-three.js        three 实现（几何构建 / 三通道 / 机位）        渲染层
projection-check.js     相机矩阵投影 + Chamfer 打分                  纯逻辑
floorplan-editor.js     校对面板（Konva，复用画布能力）               UI 层
```

**硬规则：前四个和 `projection-check.js` 不许 import three，不许碰 DOM。** 这样它们能被 `node --test` 全覆盖，而渲染层可以坏、可以换后端，不影响正确性验证。v2 说"测试全部纯 Node"，需要这条分层才真的做得到。

`graph-core.js` 改动极小：`PORT` 加 `GEOMETRY`，`NODE_DEFS` 加 `floorplan` / `massing` 两个节点定义，`generator` 加 `depth` / `edge` 两个输入口。

## 8. 分期（按改动重排）

### P0 本地链路打通（不含 DXF）

- `floorplan-schema.js`：契约 + 13 条校验 + 单测正反例
- `massing-backend.js` + `massing-three.js`：build / setCamera / render / preview
- 三通道出图 + `generator` 新端口 + 提示词追加几何约束段
- `floorplan-editor.js`：**表格 + 拖拽微调**（先不做画墙）
- `projection-check.js`：投影 + Chamfer，纯 Node 可测

验收：导入一份手写 JSON（40 段墙 / 12 洞口 / 20 体块），4 机位 × 3 通道 **< 8 秒**；同参数重跑 PNG md5 一致；13 条校验正反例全过。

### P1 DXF 主路径

- `dxf-parse.js` + `dxf-topology.js` + `dxf-layers.js`
- 图层映射模板（存项目级，可跨项目复用）
- 校对面板接入 DXF 档，标黄待确认项
- 前置拒绝：非正交墙、代理对象、单位异常，导入时明确报错

验收：一套真实住宅图，图层映射 ≤ 3 次点击 → 户型 JSON；墙段数、洞口数与人工目视逐项核对无遗漏；双线配对失败率 < 10%。

### P2 兜底与云端

- 位图识别（复用 `providers.js` 视觉配置，只填空、不终判）
- 云端 DWG → DXF（显式同意 + 不留存）
- 云端 Blender 兜异形户型与终稿阴影
- 灰模进全景节点

## 9. 风险补两条

| 风险 | 应对 |
|---|---|
| 坐标系离原点过远导致浮点抖动 | 解析后强制平移到左下角，坐标进 three 前断言在 [0, 30000] |
| DXF 图层不规范，映射猜错 | 不做自动猜；映射必须人确认，且预填常见命名（WALL/墙体/墙、DOOR/门、WINDOW/窗、DIM/标注、AXIS/轴线、FURN/家具）作为建议值 |

## 10. 需要拍板的三件事

1. **DXF 是否进 P0**：我建议进。设计师是主用户，P0 若只有手输，对他们是倒退，也不足以验证"这套东西真能用"。
2. **家具体块做不做**：v2 说必须有（否则家具位置问题没解决）。我同意，但建议 P0 只上 12 个体块（沙发/床/餐桌/衣柜/橱柜/马桶/台面/茶几/电视柜/鞋柜/书桌/浴缸），不做型号级。
3. **DWG 云转排 P1 还是 P2**：我建议 P2。V1 的"另存为 DXF"能撑住，先把本地链路和校对体验做扎实。
